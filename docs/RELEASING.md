# 정식 버전 배포 체크리스트

새 버전 배포에는 **공지 원고 작성과 텔레그램 실제 전송 확인까지** 포함합니다. GitHub 릴리스 게시만으로 배포 작업을 완료했다고 보고하지 않습니다.

## 게시 전

- [ ] VERSION과 앱의 대체 버전 문자열, README·변경 이력을 맞춥니다.
- [ ] 변경에 맞는 검사·빌드·실행 검증을 완료하고 확인한 환경과 한계를 기록합니다.
- [ ] `announcements/telegram/vX.Y.Z.txt`에 해당 버전의 공지 원고를 작성합니다. 제목·핵심 변경 사항·직접 빌드 안내·정확한 릴리스 링크·Fairy·Buy Me a Coffee·Ko-fi 링크와 스튜디오 개발 활동 전반에 대한 후원 안내를 포함합니다.
- [ ] 원고 길이와 필수 링크를 전송 스크립트의 `message()` 함수로 로컬 검증합니다. 이 함수는 텔레그램에 접속하지 않습니다. 새 릴리스가 아직 없을 때는 GitHub 미리보기 실행 대신 이 검증을 사용합니다.
- [ ] 원고와 코드를 `main`에 커밋·푸시하고, 해당 커밋의 태그로 정식 릴리스를 게시합니다. 실행 시 main에 원고가 있어야 합니다.

원고 형식은 [공지 작성 가이드](../announcements/README.md)를 참고하세요. 자동화는 원고를 생성하지 않으므로 배포 작업자가 작성해야 합니다.

## 게시 후 — 필수

- [ ] 해당 릴리스가 draft·prerelease가 아닌 정식 버전인지 확인합니다.
- [ ] [Telegram release announcement](https://github.com/Rayeonjin/Catoshi/actions/workflows/telegram-release.yml)에서 해당 버전의 자동 실행을 찾습니다. 다른 버전이나 preview_only 실행과 혼동하지 않습니다.
- [ ] 실행 종료까지 확인합니다. 실제 게시 단계가 성공했고 로그에 `Telegram announcement delivered. Message ID:`가 있는지 확인합니다. 이는 Telegram API가 메시지 게시를 수락했다는 확인이며 구독자의 열람을 뜻하지 않습니다.
- [ ] 최종 보고에 릴리스 링크와 실제 전송 결과를 함께 적습니다.

자동 실행이 없으면 이벤트 설정과 릴리스 생성 방식을 확인합니다. 다른 Actions의 GITHUB_TOKEN으로 생성한 릴리스는 후속 workflow를 시작하지 않을 수 있습니다. 기존 전송이 없음을 확인한 뒤 해당 태그로 workflow_dispatch를 실행하고 preview_only=false를 지정합니다.

전송 오류가 나면 채널에 이미 게시되었는지 먼저 확인합니다. 타임아웃은 게시 성공 뒤에도 발생할 수 있습니다. 확인할 수 없으면 전송 상태를 ‘미확인’으로 보고하고 중복 전송을 강행하지 않습니다. 토큰·채널·권한 문제는 [자동 공지 설정 가이드](TELEGRAM_ANNOUNCEMENTS.md)를 따릅니다. Secrets 값은 로그나 문서에 남기지 않습니다.

문서만 바꾸는 작업은 앱 버전을 올리거나 공지할 필요가 없습니다. 베타·초안은 현재 정식 릴리스 자동 공지 대상이 아닙니다.
